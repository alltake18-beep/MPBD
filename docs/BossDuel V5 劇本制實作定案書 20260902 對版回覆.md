# BossDuel V5 劇本制實作定案書 20260902｜對版回覆

日期：2026-09-02
比對來源：`BossDuel V5 劇本制實作定案書 20260902.md`
現行依據：Repository 現行共用核心、`Boss Duel 交接.md`、`Boss Duel 故事池數學模型.md`、`Boss Duel 產生劇本業務邏輯.md` 及 Project State

## 一、結論

整體方向大致一致：240,000 筆自然劇本、每星三分類各 10,000、建立 Boss 時三分類各抽一個再配 1,000,000 整數籤、玩家自由操作、偏離稽核、抑制專用表、三個個人劇本水池帳務桶、擊殺時合法骰面補正，以及每隻 Boss 鎖定 RTP／版本／抑制參數等主架構均有對上。

但本文件目前**不能直接視為最終定案**。主要原因如下：

1. 對版基準仍是舊版 `arrange-v9`／`natural-story-preset-v11`，未包含 2026-09-02 新增的理牌規則。
2. 進行中 Boss 的跨版本處理、持久化與一小時過期規則，直接違反現行正式需求。
3. 連殺被寫成沿用，但現行正式設定已停用。
4. 劇本通用所有 Bet 的契約沒有明確寫出。
5. 抑制參數變更被誤寫成必須重產劇本；現行設計中抑制是線上執行期規則，不參與 240,000 筆離線劇本生成。
6. 配籤容許差只在測試驗證、未於建立 Boss 時擋下，與正式文件的失敗條件不一致。
7. 目標 RTP 被研發側自行限制為整數，且平台即時調整介面仍未完成。

## 一之一、2026-09-02 後續產品定案

下列項目已由產品確認，研發文件應直接依此實作，不再列為待確認：

1. 接受工程端可重跑測試中「隨機操作玩家 RTP 約 2.3%」；96% 仍是劇本配籤目標，不保證任意偏離策略。
2. 免費換牌不扣款、不入個人劇本水池，但仍增加換牌次數、推進費率階梯並保存操作序號；若第一換免費，下一次付費換牌收第二階 2x。
3. 劇本路徑已結束但玩家仍有合法換牌或和局重發時，操作照常執行。成功換牌保存 `plannedRecordMissing=true` 並算偏離；原劇本 `killed=false` 才啟動抑制，`killed=true` 不啟動。
4. 接受同一每日 240,000 筆發布目錄採放回抽樣；不同玩家或 Boss 可重複抽中同一劇本，抽中後不移除 seed。

以下項目請修改完成並重新提供版本、程式與驗證證據後，再進行最終對版。

## 二、必須修正的差異

### 1. 版本基準已過期，舊版全量對拍不能代表現行版本

對方文件目前鎖定：

- `rules-v10`
- `boss-plan-v10`
- `arrange-v9`
- `natural-story-preset-v11`
- `deviation-suppression-v3-configurable-tables`

目前 Repository 的發布目標為：

- 遊戲：`frontend-v96`
- 機率工具：`action-tree-v35`
- 後端文件：`backend-doc-v9`
- 規劃器：`boss-plan-v11`
- 理牌：`arrange-v10`
- 正式劇本：`natural-story-preset-v13`
- 操作軌跡：`story-action-trace-v2`
- 抑制：`deviation-suppression-v4-configurable-tables`

`arrange-v10` 會改變 AI 保留牌與換牌路徑，因此 `natural-story-preset-v11` 的 240,000 筆零差異對拍只能證明舊版 Go 移植與舊版 JavaScript 一致，不能證明現行版本一致。

需修正：

- Go 引擎補入 `arrange-v10`。
- 重新自然產生 8 星 × 3 分類 × 各 10,000 筆。
- 對新 240,000 筆逐筆完整重播，不得抽樣。
- 更新版本錨、生成簽章、摘要簽章及固定測試向量。
- 提供 Go commit、JavaScript 基準 commit、產生器版本、preset／summary SHA-256、全量對拍報告。

因免費換牌費率階梯已正式更動，舊 `natural-story-preset-v12` checkpoint 不得直接續用。既有正式 seed 若要作為候選來源，必須先用 `boss-plan-v11` 逐筆重跑、按新結果重新分類，不能沿用舊摘要或舊分類；再以新 seed 補足各格 10,000，最後對 `natural-story-preset-v13` 完整 240,000 筆全量重播，才能宣稱新版通過。

### 2. 缺少 `arrange-v10` 新理牌規則

對方文件沒有下列現行規則：

1. 保留集合不區分系統自動或玩家手選；送出 REDRAW 時全部視為玩家確認。
2. 一般情況不得自動取消任何已保留牌。
3. 唯一強制覆蓋例外：REDRAW 後完整六張牌形成皇家同花順、同花順或四條時，直接改保留優先序最高的完成牌型，即使必須取消先前保留牌。
4. 五張基礎核心不再補效果牌。
5. 四張基礎核心且核心沒有暴擊或固傷時，只補一張；優先序為「同一張暴擊＋固傷」＞「暴擊」＞「固傷」。核心已帶任一效果時不補第五張。
6. 三張或兩張基礎核心最多補兩張；核心尚未帶到的暴擊與固傷牌，出現幾張就保留幾張；同一實體牌只占一格。
7. 每回合魔法卡由十種不同卡種中不放回抽兩種，不會抽中兩張相同魔法卡。

這些規則必須由遊戲、理牌試玩、Go 引擎、劇本生成與重播共用，不能只補文件或只改前端。

### 3. 必須明文補上「同一劇本通用所有 Bet」

對方文件說明了三個 Bet 帳務桶，但沒有明確寫出正式劇本本身不依 Bet 分池。

現行契約是：

```text
實際總花費 = story.spendX  × Bet
實際總派彩 = story.payoutX × Bet
實際淨值   = story.netX    × Bet
```

Bet 不得改變：

- seed
- 玩家牌、Boss 牌與牌堆
- 魔法卡種類、綁定與原始結果
- AI 保留牌、換牌與 FIGHT／FOLD 路徑
- `win`／`push`／`lose` 分類
- 24 格配額

需修正：在總述、資料結構、生成、線上還原及驗收章節明文加入 `story-bet-scaling-v1`。Bet 1、Bet 2,000 與任一新增合法 Bet 使用同一 `star + seed` 時，完整路徑必須相同，只有點數等比例縮放。

### 4. 進行中 Boss 不得因換版被擋下或免費替換

對方第五章第 5 條寫法是：不保留舊版引擎，版本不符時阻擋進行中的 Boss，讓玩家免費換一隻新 Boss。

這與正式需求直接衝突。現行要求是：

- 新 Boss 使用新版本。
- 已建立 Boss 保留原 `releaseVersion`、`rulesVersion`、`plannerVersion`、`suppressionSignature`、`targetRtpPct` 與完整房間狀態。
- 換日、換版、回滾與滾動部署都不得改變或終止進行中 Boss。
- 服務節點必須依房間鎖定版本路由到相容引擎；不得拿目前引擎交叉還原舊 Boss。
- 回滾後仍須能重播原版本。

「物化原劇本軌跡」不能取代相容舊引擎，因為玩家偏離後會進入原劇本未預先物化的換牌候選與魔法抑制分支。免費換 Boss 也不是等價處理：它會改變玩家已投入、預留、Boss 進度與預期結果。

需修正：保留可路由的版本化引擎／規則執行環境，或提出能逐操作完整重播所有偏離分支的等價實作並完成跨版本整合測試。未完成前不得以部署空窗、強制結清或免費換 Boss 代替。

另外，版本與 RTP 必須在**建立 Boss 時**鎖定，不是等到第一次 START 才決定。第一次 START 只負責扣款、入池與預留的原子交易。

### 5. Redis、持久化與一小時過期規則不符合需求，且文件內部矛盾

對方第五章第 4 條寫「不設存留期限、Redis 清空不致遺失」；第九章第 3 條又寫「無活動一小時房態過期，過期視同結束」。兩段互相矛盾。

現行正式需求是：

- 進行中的 Boss 不因登出、換裝置、伺服器重啟或一般無活動而重置。
- 暫停不結算、不補正、不釋放預留；回來時原樣續玩。
- 只有擊殺、回合用盡或玩家明確 ABANDON 才能結束並依規則釋放。
- 正式 seed、摘要、房間、操作紀錄、三桶帳本、預留與簽章必須放在版本化持久儲存。
- Redis 只作快取與目前版本指標；Redis 清空不得造成正式狀態遺失。

「一小時過期後視同結束並回收預留」會改變玩家結果，也可能造成多 Boss 同桶預留被提前釋放，不能採用。

需修正：移除一小時自動結束；提交實際持久化拓撲、備份／還原策略、Redis 清空復原測試、伺服器重啟與跨裝置續玩測試。若研發側堅持以 Redis 作唯一正式資料源，屬於規格變更，不能自行裁決為等價。

### 6. 連殺已停用，不得沿用

對方第六章寫「連殺照現行機制沿用」。現行正式設定是停用，遊戲教學、機率工具與測試亦已移除連殺文案及報表。

需修正：

- 後端不得累積或套用連殺倍率。
- 前端不得顯示連殺提示或獎勵。
- 故事生成、配籤、派彩與個人劇本水池不得包含連殺值。
- 移除定案書中的「沿用」敘述並加回歸測試。

### 7. 抑制參數改動不應重產 240,000 筆劇本

對方第八章將抑制參數與引擎版本綁在一起，並寫成修改抑制參數就必須重產劇本庫。

現行設計中：

- 240,000 筆劇本只由正常遊戲規則與規劃器生成、分類。
- 抑制只在線上玩家偏離後執行，不參與離線劇本生成與分類。
- 每隻 Boss 建立時鎖定完整抑制參數與 `suppressionSignature`。
- 中途調整只影響後續新 Boss，不改變進行中 Boss。

需修正：分開 `storyContentSignature` 與 `suppressionSignature`。只有會改變正常劇本內容或分類的參數才重產 240,000 筆；單純調整抑制啟動、候選接受率、候選上限、末候選處理或三張抑制表，不應重產離線劇本。

### 8. 配籤容許差必須在建立 Boss 時正式驗收

對方第四章與第九章第 2 條說執行期只擋零籤，不以 0.01 個百分點容許差作廢重抽。

正式文件要求：

- 三候選籤數合計必須為 1,000,000。
- 三候選都必須至少 1 籤。
- 整數化後的加權 RTP 誤差不得超過設定容許差；出廠為 0.01 個百分點。
- 任一條件失敗，整組三候選重抽；達上限則 Boss 建立失敗、不扣款、不留半筆。

研發側指出目前 JavaScript 參考程式也沒有在 `drawUniformPresetStoryCommit()` 強制檢查容許差，這個觀察是正確的；但它代表我方參考實作也需要修正，不代表後端可以沿用缺口。

需修正：Go 與 JavaScript 都在正式建立 Boss 路徑檢查 `errorPp <= tolerancePp`，並新增超標整組重抽與達上限失敗測試。

### 9. 目標 RTP 不得自行限制為整數，平台調整介面不能停留在待辦

對方第四章與第八章把目標 RTP 限為 80～99 的整數百分點，且目前仍以出廠常數承載，管理後台介面尚未完成。

現行工具與核心接受 80%～99% 之間的小數，機率工具輸入精度為 0.001。現行需求也沒有授權研發側縮限為整數。

需修正：

- 支援 80～99（含）的小數 RTP，或另提產品決策取得書面確認。
- 完成平台商可隨時調整的正式設定來源與權限控管。
- 建立 Boss 時鎖定當下值；後續改值只影響新 Boss。
- 配籤、每筆花費入池及稽核都使用同一鎖定值。

## 三、需要補充確認或證據的項目

### 10. 劇本沒有對應操作位置時的偏離處理

對方第五章第 2 條自行裁決：玩家的換牌或和局次數超出原劇本紀錄時，成功換牌一律視為不一致；只有原劇本 `killed=false` 才啟動抑制。

這個方向與「玩家操作和劇本不同時後端必須知道」相容，也符合現行抑制的兩個必要條件，但目前正式文件沒有把「planned record missing」獨立寫成判斷值。

建議正式化為：

```text
plannedKeepIds 不存在 → keepDeviation = true
但 suppressionActive 仍須同時滿足 originalStory.killed = false
且本次是成功 REDRAW
```

需補：`plannedRecordMissing=true` 稽核欄位，以及原劇本可擊殺／不可擊殺、額外換牌、額外和局三組固定測試。

### 11. 每日重用同一劇本已由產品接受

同一發布版本允許不同 Boss 重複抽到相同故事，這與目前「每隻 Boss 從完整分類獨立抽取、不排除曾抽過故事」一致，且產品已確認接受。正式契約為放回抽樣：抽中後不移除 seed；發布目錄內 seed 唯一不代表營運只能使用一次。

工程端仍須遵守：

- 玩家端永不取得 seed、完整牌序、三候選、K 值及抑制 RNG 狀態。
- 提供重複故事碰撞率、單玩家碰撞率及可辨識性評估。
- 若研發側發現可實際利用的攻擊路徑，另提安全缺陷，不得自行改為不放回抽樣。

### 12. 「兩小時完成全庫」缺少可驗證條件

對方宣稱 240,000 筆含分類篩選與全量驗收約兩小時，但沒有提供：

- CPU／RAM／作業系統
- worker 數與批次大小
- 各星實際嘗試數
- 生成與 240,000 筆全量重播各自耗時
- 峰值 CPU、峰值記憶體、暫存與正式檔案大小
- 失敗重啟及 checkpoint 恢復時間

需提供正式跑批報告。這項證據尤其重要，因第 8 星贏少是稀少分類，發布量 240,000 不代表自然嘗試量只有 240,000。

### 13. 舊版全量對拍與固定向量需要交付原始證據

目前定案書只有「已通過」結論，沒有可重跑產物。請提供：

- Go 原始碼 commit 與建置版本。
- JavaScript 基準 commit。
- 240,000 seed 清單及來源 preset SHA-256。
- 每星每分類數量、逐筆摘要差異數、首筆失敗資訊格式。
- 測試命令、輸出檔及 CI job 連結。
- `hash32`、PRNG、洗牌、骰子、排序、整數籤與金額捨入固定向量結果。

在證據可重跑前，只能標記為「研發側聲明已完成」，不能標記為我方已驗收。

### 14. 金額捨入差異需提供七筆固定案例

對方第九章第 1 條指出 JavaScript 浮點值在半個最小單位邊界可能與「0.5 遠離 0」差一個最小單位。這是合理且重要的發現。

正式帳務應以有號 64 位整數最小單位處理，Go 端不應為了對拍 JavaScript 浮點誤差而做錯誤捨入。但請提供抽驗 3,000 例中出現差異的七筆完整輸入、JavaScript 結果、精確整數結果及預期結果，並將這些案例加入雙方常駐測試。

另需確認全量劇本對拍不會覆蓋這類帳務問題，因離線劇本摘要不一定包含線上個人水池的半單位落帳邊界。

### 15. 隨機玩家 RTP 約 2.3% 已由產品接受

對方第九章第 4 條稱：貼近劇本玩家約 95.96%～95.99%，隨機玩家約 2.3%。若結果可重現，表示 96% 是「劇本承諾與配籤 RTP」，不是所有實際玩家策略都會被個人水池拉回 96%。

原因是：未擊殺時沒有 Boss 派彩，也不做骰獎補正；正水池只能等待日後實際擊殺吸收，且單次吸收仍受合法骰面與原獎 1,000% 上限限制。玩家永久流失時，正餘額可能永遠留在帳上。

產品已明確接受極端偏離玩家不保證接近設定 RTP；不得為了把隨機玩家拉回 96% 而改寫劇本、強制玩家操作或放寬擊殺補正邊界。工程端仍須提供以下可重跑證據，供版本驗收與後續觀察：

- 各策略完整參數、隨機種子、玩家數、Boss 數、Bet 分布與擊殺率。
- 三桶期末餘額分布、玩家流失率及流失時未吸收正負餘額。
- 玩家之後恢復正常操作時，水池回收至接近零所需 Boss 數分布。
- 各星補正容量、合法骰面跳格與 1,000% 上限受限比例。
- 產品側確認日期及適用版本。

### 16. 固定指定劇本體驗的範圍要說清楚

對方寫「本次不啟用、未實作」，但我方遊戲與機率工具已有指定正式 seed 的 QA 體驗流程。正式玩家不一定需要此功能，但後端至少要能以測試權限指定 `releaseVersion + star + seed`，才能完成端到端重播與工程驗收。

需確認：現有測試注入是否能完整覆蓋指定故事、相同操作重播、偏離後候選、抑制魔法及結算；若可以，可標記為「只在測試環境提供」，不必開放給正式玩家。

## 四、對方指出且我方需要修正／釐清的問題

### 17. `suppression-v2`／`suppression-v3` 舊 preset 簽章不一致

此問題確認存在：舊 `natural-story-preset-v11`／summary 內的 `generatorRevision` 標示 `suppression-v2`，而現行 generator 常數已是 `suppression-v3`；嚴格執行 `validatePreset()` 會得到 `SIGNATURE_MISMATCH`。

對方說 configSignature 相同且舊 240,000 筆可重播，能說明故事內容可能未受抑制版本影響，但不能消除跨檔簽章不一致。

處理方式：不修改舊檔假裝一致；由 `boss-plan-v11`／`arrange-v10`／`natural-story-preset-v13` 正式重建時產生一致的新 preset、summary、diagnostics 與 manifest，並重新做 240,000 筆全量重播。

### 18. 後端文件案例 B、C 的玩家畫面文字確有錯誤

對方指出的兩處成立：

- 案例 B：帳務與原骰面都是 `[3] × [2] = 6x = 60`，玩家畫面不應寫成 `[4] × [2] = 8x = 80`。
- 案例 C：帳務最後採用合法骰獎 40，因此玩家畫面應為 `4x = 40`，不應寫成 `2x = 20`。

這兩處是敘述與同案帳務不一致，需在下一版後端文件修正並加 HTML 契約檢查。

### 19. JavaScript 金額捨入應改成可證明的整數契約

目前核心 `toMoneyUnits()` 仍由 JavaScript 浮點乘上 10,000 後加 0.5 取整。一般案例可通過，但精確半單位可能受二進位浮點表示影響。

後續應以字串／高精度小數或分子分母轉成最小單位，再做 0.5 遠離 0；修正前先取得對方七筆固定案例，避免雙方各自選不同邊界。

### 20. 舊 `natural-story-preset-v12` 不得作為新版本完成證據

`boss-plan-v11` 改變免費換牌之後的費率、花費與 AI 路線，因此舊 `natural-story-preset-v12` checkpoint、分類與摘要雜湊都不能作為新版本驗收證據。既有 seed 只能逐筆以新規則重跑並重新分類後作為候選，缺額必須補入新 seed；`natural-story-preset-v13` 仍須以新 manifest 的實際數量、240,000 筆全量重播結果與 SHA-256 更新正式交接。
